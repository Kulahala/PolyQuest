## Active Stage: TODO-03A1 - Equipment Domain, Weapon Definition, And Hand-Slot Contract v1

Baseline: `601ad38 [Feature] 玩家装备与战斗 Loadout 基础 (Equipment And Combat Loadout Foundation)`.

### Objective

Replace the deliberately narrow single-StaticMesh equipment assumption with the reviewed equipment-domain contract before any new weapon category: a `UWeaponDefinition` base class with `UMeleeWeaponDefinition` retained as the compatible melee subclass, `UCombatActionDefinition` reference-list assets, MainHand/OffHand/TwoHanded hand-slot rules, `UWeaponEquipmentComponent` as the single input-resolution and prepared-slot runtime owner, and the MainHand-fallback/OffHand-override Defense Profile contract. The TODO-03A transaction, runtime markers, and trace ownership are preserved; the enemy fixed-marker fallback is untouched. This stage delivers the domain types and ownership rewiring plus the Sword route regression - Unarmed combat, world pickup, the Shield asset, enemy presets, and Bow remain TODO-03A2 through TODO-03B.

Locked values (user-locked contract):

- **Preserved TODO-03A results:** the `EquipWeapon` validate/snapshot/teardown/apply/restore transaction (including the Primary-arbitration and foreign-spec preflight gates), runtime-spawned display and markers, weapon-owned sweep shape in `UMeleeTraceSourceComponent`, the player-first/fixed-name-fallback trace resolution, and the enemy fixture are all retained. The enemy fixed Marker fallback is not removed.
- **`UWeaponDefinition` base class** (`Combat/Equipment/WeaponDefinition.h`, abstract): authored fields for `WeaponMesh` (nullable to admit a future Unarmed hand-contact subclass), `AttachSocketName`, display offsets, `EWeaponHandSlot HandSlot` (`MainHandOneHanded` / `MainHandTwoHanded` / `OffHand`), `ReusableCombatActions` and `ExclusiveCombatActions` (`TArray<TObjectPtr<UCombatActionDefinition>>`), `DefaultPreparedActions` (zero to four authored defaults for the fixed runtime `1-4` layout), and one optional Defense Profile reference. `IsValidWeaponDefinition(FString&)` validates slot/display/composition rules; subclasses extend it. `UMeleeWeaponDefinition` derives from it unchanged in field name and serialization (`AssociatedLoadout` keeps its UPROPERTY name and is re-documented as the Base Input Profile; no rename, no CoreRedirect), still owns markers/sweep shape, and keeps `GrantedWeaponAbilities` as the compatibility grant source.
- **`UCombatActionDefinition`** (`Combat/Equipment/CombatActionDefinition.h`, DataAsset): a reference list only - `AbilityClass` (`TSubclassOf<UGameplayAbility>`) and an optional semantic `ActionIntentTag`. It does not own Montage, GameplayEffect, damage, tuning, input, targets, or cooldown state; the existing GA Blueprint authoring remains the presentation/effect configuration owner. Motion Warping gets no speculative fields.
- **`UCombatLoadoutDefinition` migrates semantically into the MainHand Base Input Profile.** The class and the existing `DA_CombatLoadout_StraightSword` asset are untouched; its non-slot routes (`Input.PrimaryAttack`, `Input.Guard`, `Input.Parry`, Sprint Attack) become the MainHand definition's Base Input Profile via `AssociatedLoadout`, while its `1-4` route entries are simply no longer consumed - prepared slots own `1-4` from now on. The old authored slot entries may remain in the asset without effect.
- **`UWeaponEquipmentComponent` becomes the single input resolver and prepared-slot runtime owner.** It holds `CurrentMainHandWeapon`, `CurrentOffHandWeapon`, and `PreparedActionSlots[4]` with their granted spec handles. `EquipWeapon(Definition)` routes to the slot from `HandSlot` through the same fail-closed transaction extended with composition preflight: equipping an OffHand item while a TwoHanded MainHand is equipped is rejected; equipping a TwoHanded MainHand while an OffHand item is equipped is rejected in this stage (TODO-03A3 owns the combined drop-swap transaction). The prepared layout rebuild is **keep-if-compatible**: after a successful swap, an old slot entry survives when its `UCombatActionDefinition` is still a candidate of the new composition and resolves to exactly one compatible grant, then remaining empty slots fill from the composed defaults in MainHand -> OffHand order. Rollback semantics are exact: a **preflight failure causes zero handle changes**; an **apply failure restores the old weapon composition and the prepared slots' `UCombatActionDefinition` identities, re-grants them through `GiveAbility`, and rebuilds the slot bindings on the new handles**. `TryActivatePreparedSlot` validates on every call that the handle is valid, belongs to this component's current grants, and that its ability class still matches the slot's `UCombatActionDefinition`. Validation never compares old/new handle values - it verifies no residual specs and exactly one valid freshly-bound handle per restored slot.
- **Grant sources coexist:** the melee subclass's `GrantedWeaponAbilities` is not a fallback that turns off when combat actions exist - it is the **BaseGrantedAbilities** source that the current Sword asset relies on for its LMB/Sprint base chain (`GA_PrimaryAttack` arbitration depends on already-granted Light/Charged specs). Base grants and prepared-action grants are applied together, and any duplicate ability class between them (or within either list) fails the preflight closed. Removal of `GrantedWeaponAbilities` happens no earlier than TODO-03A2's full authoring migration, and only after a source scan plus Editor readback show zero referencers.
- **Input resolution contract:** `APlayerCharacter::RequestAbilityForInputIntent` delegates to the component as the only resolver. The Base Input Profile resolves **only** `Input.PrimaryAttack` and the Sprint Attack route. `Input.Guard`/`Input.Parry` resolve exclusively through the Effective Defense Profile - the OffHand definition's profile first, then the MainHand definition's profile, then the built-in `Ability.Defense.Guard`/`Ability.Defense.Parry` defaults; the profile's Guard/Parry route entries are never consumed. `Input.AbilitySlot.1-4` activate `PreparedActionSlots` through their exact `FGameplayAbilitySpecHandle` - never through a tag route table. With the current Sword data the resolved behavior is byte-equivalent to the TODO-03A route.
- **`UDefenseProfileDefinition`** (`Combat/Equipment/DefenseProfileDefinition.h`, DataAsset): exactly `GuardAbilityTag` and `ParryAbilityTag` (defaults `Ability.Defense.Guard`/`Ability.Defense.Parry`), with no reserved presentation fields - TODO-03A4 adds Shield presentation fields when that stage exists. Carried by a MainHand definition it is the fallback (the future Bow route); carried by an OffHand definition it overrides the fallback (the future Shield route). Guard/Parry GA classes stay in `StartupAbilities`; this stage only rewires which tag the physical inputs resolve to.
- **Editor data-retention readback gate:** moving the display fields from `UMeleeWeaponDefinition` up to `UWeaponDefinition` must preserve the serialized values of the existing `DA_MeleeWeapon_Sword` (UE serializes UPROPERTYs by name across the inheritance chain). The user's Editor readback confirms every migrated field still holds its authored value before PIE runs; any observed loss is a stage blocker, not a re-authoring task.
- **03A1 permits only the default Guard/Parry tags.** The Effective Defense Profile chain is the contract, but this stage's data and PIE evidence cover only `Ability.Defense.Guard`/`Ability.Defense.Parry`. Adopting non-default tags in TODO-03A4 first requires migrating every direct Guard/Parry tag query, cancellation, and restore call inside the player code (`FindActiveGuardAbility`/`CancelActiveParry`/Guard-Break cancel sets and the resume path) to resolve through the Effective Defense Profile; that support must not be claimed as implemented before then.
- **Forbidden by contract:** no CoreRedirects; no renaming of existing DataAssets or UPROPERTYs; no moving Montage/GE/presentation configuration into `UCombatActionDefinition`; no removal of the enemy fixed Marker fallback; no reuse of `UChargedAttackAbility` for a future Bow; no world pickup, Unarmed combat, Shield asset, enemy preset, inventory, or persistence work in this stage.

### Native Contract (draft)

- `UWeaponDefinition::IsValidWeaponDefinition` validates its authored display/action/defense references: a non-none socket, no duplicate `UCombatActionDefinition` between reusable and exclusive lists, at most four `DefaultPreparedActions` entries that exist in the combined candidate lists, and a null-or-valid Defense Profile. `RunPreflight()` then validates the proposed composition's BaseGrantedAbilities and computed prepared actions, rejecting missing ability classes, duplicate grants, `StartupAbilities` collisions, and foreign ASC specs before any mutation.
- `UWeaponEquipmentComponent` keeps the public surface `bool EquipWeapon(UWeaponDefinition*)` plus two new narrow C++ query entries: `bool TryResolveInputIntent(const FGameplayTag& InputIntentTag, FGameplayTag& OutAbilityTag)` and `bool TryActivatePreparedSlot(int32 SlotIndex)` (exact spec-handle activation, never tag-routed). Teardown, snapshot/restore, and the combat-state gate are shared by both slots, and the snapshot/restore now covers the prepared layout and its handles in full. The display/markers/trace of the MainHand remain the only melee trace source in v1 (an OffHand item never contributes melee markers this stage).
- `APlayerCharacter` wires `RequestAbilityForInputIntent` and the ability-slot started handlers to the component, keeps `SetActiveCombatLoadout` as the internal apply path the component calls with the equipped MainHand's Base Input Profile, and drops no other player contract. `ABaseCharacter`, the enemy classes, `UAbilityTask_MeleeTraceWindow`, and `FMeleeHitResolver` are not modified.
- `UMeleeTraceSourceComponent` reads the equipped MainHand exactly as in TODO-03A; no signature or fallback change beyond tolerating the base-class pointer.
